# 主动缓存的轻量可用空间检查

日期：2026-10-25。API36项目模拟器，普通debug/store配置。本轮继续落实主动缓存、长期磁盘增长与控制耗电要求；未提交、推送、发版或更改品牌。

## 发现与改动

旧 `DiscoveryController.prefetchWindow` 为判断是否能预读，周期性调用 `DataStorageBudget.measure` 遍历整个私有数据树。该统计最多访问20,000个节点或运行2秒；未统计完整时 `Snapshot.allowsPrefetch` 返回false。由于最新策略没有总占用2GB硬上限，预读的磁盘条件实际是可用空间，不再需要完整占用分类。因此文件较多时，旧逻辑会重复执行与预读无关的目录统计，并可能因统计不完整而持续阻止主动缓存。

现在将两项职责分开：

- `DataStorageBudget.freeSpace` 仅校验数据目录并查询文件系统可用空间，不枚举正文、模型、WebView或登录目录。只有空间已确认且至少64MiB时允许预读；查询失败、目录缺失或空间不足仍拒绝。
- 发现页沿用15秒空间检查结果复用及原worker/generation/epoch边界。正文和图片共用该空间判定；清缓存会使结果失效，下一窗口重新检查。
- `storageStatus` 用户主动查看用量时仍执行有界完整分类统计；统计未完整时如实注明，不再修改预读空间检查结果。占用分类不完整和可用空间无法确认是两种情况。
- 不修改LRU、正文96MiB/图片128MiB派生缓存的内部上限、缓存会话隔离、收藏/反馈/进度、模型、来源开关或线程数量。内部有界缓存不等于恢复旧的App总占用2GB、独立150MB RAM/300MB磁盘限制。

这证明预读路径不再主动调用整个目录统计，不据此宣称实际手机省电百分比、所有存储IO已消失或整App资源门槛已通过。手动用量统计仍有原有时间/节点上限。
