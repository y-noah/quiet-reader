# 待接收批次与跨 URL 后续报道进展

本轮有生产实现变化，目标仍未全部完成。没有访问手机、更新 current-candidate、推送或发版。普通候选仅归档本地并在保留数据的 API36 模拟器验证。

## 实现与准入

旧 Controller 只从 allRows（当前已显示批次）收集正文进展候选。现在 ArticleProgressPreparation 在 storage 线程读取用户实际请求接收的 snapshot，最多读取5000行、收集128个支持新闻正文进展的成员；新 pending 中的成员也能进入证据预筛。只有可能存在证据的 URL 返回 UI 捕获账号令牌，普通无证据路径不全量读取 Cookie。

新增跨 URL 后续报道比较，复用 schema9 的 article_progress，不增加表、后台服务、抓取、定时器或模型调用：

1. 两个 URL 必须同属当前待接收快照已接受的事件；不据此产生新合并关系。此前成员须存在真实展示/有效阅读对应的正文基线，仅抓取不足以建立基线。
2. 后续正文必须属于该事件当前选定的代表文章。这样重新推荐的卡片打开新报道，同时保持既有平台代表选择策略；不会因另一个隐藏入口有更新而把仍打开旧文的卡片推回来。
3. 沿用已支持新闻来源的可信更新时间、完整中文正文准入及显式“更新/后续报道”等段落标记。正文须保留至少80%的基线指纹，至少一半新文指纹可对应旧文，并新增至少96个指纹，其中至少64个处于标记段落。时间须晚于基线采集、展示及整事件最近展示/阅读。不是事实真假或语义重要性的分类器。
4. 两篇文章分别验证其精确身份与当前账号/缓存scope；不能把一篇文章的登录范围转给另一篇。最终发布仍检查所有scope与动作代次；分组或代表文章变化会使证明不适用。
5. 对准备阶段的两份证据保留摘要，排名事务内重新核对正文载荷与展示时间。正文撤回、基线改变、清理记录、账号变化或较晚的事件曝光/阅读，都不能继续使用旧证明。
6. 每次动作最多比较16对，最多解码1MiB序列化指纹载荷；这是载荷处理上限，不是额外 Java 堆内存的测量结果。复用原256条/7天/8MiB逻辑存储限制。所有解码/散列在后台线程完成。

## 失败记录

首次 `r8-article-followup.txt` 为8项3失败，原驱动保留在 `r8/test-first.apk`。夹具直接改写某个snapshot的groupEntries，把生产去重器不会合并的两个不同标题人工装成一组；真实刷新可能接收/重建不同批次，因此它不能作为生产接受分组的正向前提。
